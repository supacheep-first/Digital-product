## บริบท

เจ้าของโปรเจกต์ต้องการหาตลาด digital product เพื่อสร้าง passive income แต่**ยังไม่มีความรู้เรื่องนี้** และ**ยังไม่ได้เลือกทิศทางใด ๆ**

**เหตุการณ์ที่นำมาสู่การตัดสินใจนี้:** ในการสนทนาแรก Claude ทำผิด 2 อย่าง
1. **ชี้ทางเร็วเกินไป** — เสนอเส้นทาง A/B/C ให้เลือก ทั้งที่เจ้าของโปรเจกต์ยังอยู่ในโหมดสำรวจ ไม่ใช่โหมดตัดสินใจ
2. **ตั้งโจทย์ research แบบเอียง** — anchor กับอาชีพ "dev 10 ปี" ทำให้ recon ทั้ง 4 ตัวไปหาแต่ข้อมูลฝั่งขาย (supply-side) และ dev-centric **ไม่มีข้อมูลฝั่งคนซื้อเลยแม้แต่นิดเดียว** และใช้ข้อมูล Gumroad (แพลตฟอร์มที่มีสัดส่วน dev สูงผิดปกติ) เป็นตัวแทนภาพตลาดทั้งใบ

เจ้าของโปรเจกต์เป็นคนทักท้วงเอง ไม่ใช่ Claude ตรวจพบ — **นี่คือสัญญาณว่าต้องมีระบบตรวจสอบที่ไม่พึ่งความระมัดระวังของ Claude เอง**

## ทางเลือกที่พิจารณา

| ทางเลือก | ข้อดี | ข้อเสีย | ความเสี่ยง |
|---|---|---|---|
| **A. ทำงานแบบ ad-hoc ต่อไป** (ไม่มีโครงสร้าง) | เริ่มได้ทันที ไม่เสียเวลาตั้งระบบ | ความรู้หายทุก session, ทำผิดซ้ำ, ไม่มีใครค้านเมื่อ Claude มั่นใจผิด | สูง — ปัญหาเดิมจะเกิดซ้ำ |
| **B. ทีม agent เล็ก 4-5 ตัว** เฉพาะที่ใช้ตอนนี้ | เบา ไม่รก | ต้องมาสร้างเพิ่มทีหลังตอนกำลังยุ่ง; เจ้าของโปรเจกต์ไม่เห็นภาพว่าสายงานนี้มีบทบาทอะไรบ้าง | กลาง |
| **C. ทีมเต็ม 16 ตัว ครอบคลุม 0→เงินเข้าบัญชี** | เห็นภาพทั้งสายงาน, เตรียมพร้อมทุก stage, เจ้าของโปรเจกต์เรียนรู้ว่าอุตสาหกรรมนี้มีใครทำอะไรบ้าง | สร้างครั้งแรกนาน, บางตัวจะไม่ได้ใช้อีกหลายเดือน | ต่ำ (agent ที่ไม่ได้ใช้ไม่ได้ทำอันตราย) |

## สิ่งที่ยังไม่รู้ตอนตัดสินใจ

- **ไม่รู้ว่าตลาดหน้าตายังไง** — นี่คือเหตุผลที่ Stage 0 ต้องมาก่อนทุกอย่าง
- ไม่รู้ข้อจำกัดจริงของเจ้าของโปรเจกต์ (เวลา/งบ/ความเสี่ยงที่รับได้/ยอมขึ้นหน้าไหม)
- ไม่รู้ว่า agent แต่ละตัวจะทำงานได้ดีแค่ไหน — ยังไม่เคยรันจริง
- ไม่รู้ว่า 16 ตัวมากไปหรือน้อยไป
- ไม่รู้ว่า domain knowledge 10 ปีของเจ้าของอยู่สายไหนกันแน่ (web/backend/data/infra? อุตสาหกรรมไหน?) — ซึ่งอาจเป็น unfair advantage ที่แท้จริง

## การตัดสินใจ

**เลือก C** — สร้างทีมเต็ม 16 ตัว + สายพาน 7 stage + โครงสร้างโปรเจกต์ที่บันทึกความรู้ถาวร

**เหตุผล:**
1. เจ้าของโปรเจกต์ขอเอง ("สร้างทีม agent สำหรับ flow ทั้งหมด ตั้งแต่ 0 จนถึงได้รับเงินจริง")
2. เจ้าของโปรเจกต์บอกว่า "ไม่รู้ว่าสายงานนี้มีใครทำหน้าที่อะไรบ้าง" → ทีมเต็มทำหน้าที่เป็นแผนที่ของอุตสาหกรรมไปในตัว
3. agent ที่ยังไม่ถึงเวลาใช้ ไม่มีต้นทุนในการมีอยู่

**มาตรการแก้ปัญหาที่เกิดขึ้นจริง (สำคัญกว่าตัวทีม):**
1. **กฎข้อ 1 ใน CLAUDE.md: "ห้ามชี้ทางถ้าไม่ได้ถูกขอ"** — ผูกไว้กับทุก session
2. **`red-team` มีภารกิจพิเศษตรวจสอบ Claude เอง** — ตรวจว่าชี้ทางโดยไม่ถูกขอไหม แสดงตัวเลือกครบไหม มั่นใจเกินหลักฐานไหม
3. **`market-cartographer` ถูกสั่งให้ถ่วงดุล bias โดยเจตนา** — ถ้ารายงานออกมาแล้วยังพูดถึงแต่สินค้าสาย dev = ถือว่าล้มเหลว
4. **`niche-scout` ถูกบังคับว่าอย่างน้อย 1/3 ของโอกาสต้องไม่ใช่สายเทค**
5. **ระบบป้ายหลักฐาน ✅/⚠️/❓** + `fact-checker` — เพราะผลค้นหาปี 2026 เต็มไปด้วย AI slop
6. **Gate ที่ต้องผ่านก่อนไปต่อ** — กันการตัดสินใจด้วยความรู้สึกหรือความเบื่อ
7. **knowledge/99-open-questions.md** — บันทึกสิ่งที่ไม่รู้อย่างเป็นทางการ

## เงื่อนไขที่จะทำให้กลับมาทบทวน

- **ถ้ารัน Stage 0 แล้วผลยังเอียงไปทาง dev อีก** → ปัญหาไม่ได้อยู่ที่ prompt ของ agent แต่อยู่ที่วิธีตั้งโจทย์ ต้องรื้อใหม่
- **ถ้าผ่านไป 1 เดือนแล้วมี agent เกิน 6 ตัวที่ไม่เคยถูกเรียกใช้เลย** → ทีมใหญ่เกินไป ให้ยุบรวม
- **ถ้า gate กลายเป็นอุปสรรคที่ทำให้ไม่มีอะไรคืบหน้า** → gate เข้มเกินไป ให้ผ่อน
- **ถ้าเจ้าของโปรเจกต์รู้สึกว่ายังถูกชี้ทางอยู่** → กฎข้อ 1 ยังไม่ทำงาน ต้องหาวิธีบังคับที่แข็งกว่า text ใน CLAUDE.md
